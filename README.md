# Better Intra Worker

Backend 'cloud' worker for the Better Intra extension, managing user synchronization and persistence via Cloudflare KV and D1.
Deployed with `npx wrangler deploy` (this repository has no CI workflow).

This deployment serves the **Intra-login build** of the extension: no 42 OAuth application, no Discord bot, no R2 bucket. Everything that needed one of those in the upstream worker (42 OAuth `/login` and `/callback`, evaluation reminders and their crons, Discord linking, image hosting, the students directory, logtime history, the 42 API proxy, project refresh) has been removed rather than left answering errors. `wrangler.json` declares `"crons": []` on purpose: the empty array is what makes `wrangler deploy` delete the schedules still registered on the live worker.

## Routes

| Route | Auth | Notes |
| --- | --- | --- |
| `POST /auth/intra` | Intra v3 Keycloak JWT in the body (32 KB at most) | Opens a session; writes the KV record and, on the first sign-in only, a `users` row. The session is stored first: a D1 error on the `users` row is logged and the sign-in still answers its token. |
| `GET /api/v1/private/settings?login=<hash>` | Bearer session | Add `&fields=meta` for `{activeSessions, discordId: null}` without the settings blob. |
| `POST /api/v1/private/settings?login=<hash>` | Bearer session | Merges `{settings}` into the record. Too large: `413` with a JSON body naming the key (see Limits). |
| `DELETE /api/v1/private/settings?login=<hash>[&all=true]` | Bearer session | Removes the calling session; `all=true` is "Wipe all data" (see below). |
| `GET /api/v1/public/visuals?login=<hash>` | none | Public visuals of one profile, `Cache-Control: public, max-age=300`. |
| `GET /api/v1/public/visuals?logins=<h1>,<h2>,...` | none | Same, for up to 50 hashes in one call: `{"visuals": {<hash>: {...}}}`. Unknown hashes get the defaults, like the single form. 120 calls a minute per IP (see Limits). |
| `POST /api/v1/private/images?slot=avatar\|banner\|background` (raw image body, 2 MB, PNG/JPEG/GIF/WebP by magic bytes), `DELETE /api/v1/private/images?slot=`, `GET /img/<hash>/<slot>?v=` | Bearer session / none | Profile images uploaded from the editor, one KV value per slot (a new upload replaces the old), stored without their metadata (see Limits); `POST` answers `{"url": ".../img/<hash>/<slot>?v=<n>"}`. `GET` with the `v` of the stored upload serves it with `Cache-Control: public, max-age=31536000, immutable`; any other `v`, or none, answers `302` to the current `?v=` with `Cache-Control: no-store` and CORS headers, so a superseded URL saved in a profile or a history shows the current image instead of breaking, and no URL is ever cached with bytes it does not name. `404` only when the slot is empty. `DELETE` removes that slot: `204` (also when it was empty), write rate limit. Wipe deletes all three. |
| `POST /api/v1/private/calendar/token`, `DELETE /api/v1/private/calendar/token`, `POST /api/v1/private/calendar/update`, `GET /calendar/<token>.ics` | Bearer session / opaque token | Calendar links. `POST .../token` registers a new link; `DELETE` is "Stop sharing": revokes the link and deletes the stored calendar (`204`, write rate limit). `.../update` then answers `410 {"error":"calendar_stopped"}` while the login has links and none is live, until a new one is registered (a login with no link row, legacy links only, is not affected). |
| `POST /api/v1/private/subjects/report`, `GET /api/v1/private/subjects/state` | Bearer session | Subject tracker. |
| `GET /api/v1/cluster/svg?url=`, `GET /api/v1/cluster/svgs` | none | Cluster maps (SVGs from `https://*.intra.42.fr` only). |
| `GET /api/v1/public/announcement`, `POST` with `{secret, message, level?, links?}` (16 KB at most) | operator secret in the JSON body | Banner shown in the extension. An empty `message` clears it; the secret never goes in a query string (`DELETE` is gone). Unset `ANNOUNCEMENT_SECRET` closes the route. |
| `GET /api/v1/public/stats` | none | Community counter (see "Data kept in D1"): totals and new users; `countries` is always `[]` (kept for extension builds up to 1.13.x, which read it). |
| `GET /gh/*` | none | GitHub raw proxy for campus data. |

Anything else answers 404 before touching KV or D1. Every private route answers one and the same `401 Unauthorized` for a missing header, a wrong token and an unknown login (the login parameter is sha256 of a public login, so a distinct "not found" would tell anyone who uses the extension); the check runs before the KV read, so anonymous scans cost no read. The `login` parameter must be a login hash (64 lowercase hex characters).

## Limits

- **Rate limits** (`src/rate-limit.ts`): 10 writes a minute per login hash (sign-in once the token is verified, settings push, wipe, calendar link, stop and upload, image upload and delete, subject reports; signing out is not limited), 30 well-formed `/auth/intra` attempts a minute per IP before any key work, and 120 batch visuals calls a minute per IP before the bulk read (each call reads up to 50 keys, missing ones billed too: without it about 2,000 anonymous calls spend the 100,000 daily KV reads; a student sends one batch per friends list every 10 minutes, so a campus NAT stays far below). The single-login visuals route and `/img/` are not limited: one read per call is the same ratio as the 100,000 daily Worker requests. Over a limit: `429` with `Retry-After: 60`. A push that changes nothing is neither written nor counted. The Workers rate limit bindings in `wrangler.json` (`WRITE_RL`, `ANON_RL`, `VISUALS_RL`, free on every plan) are used when bound; otherwise (local dev, tests, a fork without them) an in-isolate fixed window stands in. Both are best effort per colo/isolate: they make abuse slow and attributable, they do not make the shared 1,000 KV writes a day unexhaustible.
- **Size caps**: settings push body and merged record 256 KB, any single string value 64 KB (a custom stylesheet, and the Customize presets that each copy it, went past the former 8 KB / 64 KB for real students), calendar upload 256 KB (`413`), calendar token body 4 KB, image 2 MB (`413`), and the two unauthenticated bodies, `/auth/intra` 32 KB and the announcement `POST` 16 KB (`413`, read before any other check). Bodies are dropped as soon as they go over, never buffered whole. A settings push over a cap answers `413` with `{"error":"too_large","key":<the string over 64 KB, the largest key of a record over 256 KB, or null for a body refused before parsing>,"max":<the cap>,"message":"Setting CUSTOM_CSS too large (max 64 KB)"}` (record: `"Settings too large (max 256 KB); largest: CUSTOM_PRESETS"`, body: `"Settings too large (max 256 KB)"`).
- **Image metadata** (`src/image-strip.ts`) is removed on upload, on the bytes (no re-encoding: pixels, animation and ICC colour profiles stay): JPEG keeps APP0, APP2 ICC and APP14 Adobe and drops every other APPn (Exif, XMP, IPTC, MPF...) and COM, plus anything after the first EOI (MPO frames, motion-photo videos, trailers); an Exif Orientation other than 1 is written back as a one-tag Exif block. PNG drops eXIf, tEXt, zTXt, iTXt, tIME, caBX and what follows IEND. WebP drops EXIF and XMP chunks and their VP8X flags and rewrites the RIFF size. GIF drops comment extensions and every application extension but NETSCAPE2.0/ANIMEXTS1.0 (loop) and ICCRGBG1012. A file that does not parse is refused (`415`), never stored raw.
- **Public visuals** are bounded again when served (URLs 2,048 characters, words and colours 64, numbers must be finite), so a record stored by an older worker is never re-served to every visitor as is. The `logtime` block carries display values only (colours, emoji, emoji value, rainbow palette): `LOGTIME_EMOJI_RATE` is not published (the extension long labelled it "Hourly Earning", so it can hold a real pay); visitors count with their own rate.
- **CORS preflights** carry `Access-Control-Max-Age: 86400` (Chrome caps at 7,200 s), so an authenticated call is one invocation, not two.

## Data kept in D1

- `users` (`hash`, `created_at`): one row per student who ever signed in, written on the first sign-in only; it feeds the totals of `/api/v1/public/stats` (hub About tab). The `country` column is no longer written or served. Rows from before still hold the two-letter country of their first sign-in until the operator clears them (see Operations notes); the column stays so no migration is needed.
- `calendar_ics`, `calendar_tokens`: calendar links, see below.
- `subjects`, `projects`: the subject tracker registry (`projects` is read-only here; empty means `name: null`).
- A database created by the earlier schema also carries the 42-application tables (`eval_*`, `outstanding_*`, `*_stats_cache`, `logtime_history`, `cursus`) and extra `users` columns; nothing reads them any more, drop them by hand when convenient. `schema.sql` describes a fresh database.

## Data kept in KV

- `<login hash>`: the user record, `{sessionTokens (10 at most), settings}`, 256 KB at most.
- `img:<login hash>:<slot>`: the uploaded image of that slot (metadata removed), with KV metadata `{type, v}`; `v` is the version its URL must carry.
- Small caches: `INTRA_JWKS_CACHE`, `ANNOUNCEMENT`, `CLUSTER_SVG_URLS`, legacy `CALENDAR_TOKEN_*`.

**Wipe all data** (`DELETE ...&all=true`) deletes, in this order: the calendar (revokes every link, deletes the stored ICS), the `users` row (the student leaves the community counter), the uploaded images, then the KV record with its sessions and settings. A failure in an earlier step leaves the record, and so the session, for a retry. Revoked calendar-link tombstones stay, so a wiped link can never be registered again.

## Operations notes

- **Calendar links** live in the D1 table `calendar_tokens`, created on first use (also in `schema.sql`). One live link per login: "Regenerate" revokes the previous link, "Stop sharing" (`DELETE .../calendar/token`) and "Wipe all data" revoke every link and delete the stored calendar, and a revoked link answers 404 and can never be registered again. After a stop, uploads answer 410 until a new link is registered, so a second browser that restored the synced `CALENDAR_SYNC_TOKEN` cannot put the timetable back. Links made before this table (KV keys `CALENDAR_TOKEN_*`) keep working until their owner makes a new link or wipes. Rolling back to a worker without the table would break the links made since and bring the revoked legacy ones back.
- `/api/v1/cluster/svg` only fetches SVGs from `https://*.intra.42.fr`; the subject tracker only fetches PDFs from `cdn.intra.42.fr` and `projects.intra.42.fr`.
- Unhandled errors come back as JSON 500 (`{"error":"server_error","message":...}`) with CORS headers, and are logged as `[worker] unhandled error: <METHOD> <path> <name>: <message>` (path only, never the query string). `observability.logs.invocation_logs` is off so that `/calendar/<token>.ics` URLs are not persisted in Workers Logs; turn it back on if per-request status/duration is worth that.
- **One-off clean-ups**, by hand, each only with the owner's consent (they touch the live data): images uploaded before metadata removal existed go through `node scripts/strip-image-metadata.mjs --remote` (a dry run listing what would change), then `--apply` (one KV write per image that still carries metadata, metadata `{type, v}` kept so published URLs stay valid; a second run writes nothing). The countries stored before the change go with `npx wrangler d1 execute better-intra-d1 --remote --command "UPDATE users SET country = NULL"`. Neither runs at deploy.
- Tests: `npx vitest run` (in-memory KV, SQLite-backed D1 with `schema.sql` applied, rate limit stub in `tests/helpers/fake-env.ts`). Types: `npx tsc --noEmit -p .`.
