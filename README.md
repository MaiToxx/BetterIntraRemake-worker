# Better Intra Worker

Backend 'cloud' worker for the Better Intra extension, managing user synchronization and persistence via Cloudflare KV and D1.
Deployed with `npm run deploy` (see [Deploy and roll back](#deploy-and-roll-back); this repository has no CI workflow).

This deployment serves the **Intra-login build** of the extension: no 42 OAuth application, no Discord bot, no R2 bucket. Everything that needed one of those in the upstream worker (42 OAuth `/login` and `/callback`, evaluation reminders and their crons, Discord linking, image hosting, the students directory, logtime history, the 42 API proxy, project refresh) has been removed rather than left answering errors. `wrangler.json` declares `"crons": []` on purpose: the empty array is what makes `wrangler deploy` delete the schedules still registered on the live worker.

## Routes

| Route | Auth | Notes |
| --- | --- | --- |
| `POST /auth/intra` | Intra v3 Keycloak JWT in the body (32 KB at most), issued to a client listed in `JWT_ALLOWED_AZP` | Opens a session in D1 (see Sessions). Only a login's first session writes the KV record (`{"settings": {}}`, when there is none) and, on the first sign-in ever, a `users` row; any other sign-in spends no KV write. The session is stored first: a D1 error on the `users` row is logged and the sign-in still answers its token. The record counts in the daily write budget (see Limits); past the budget, or when KV refuses the key twice, it is left to the first push (a missing record reads as empty settings) and the sign-in still succeeds: a sign-in never answers `daily_write_budget` or `kv_busy`. |
| `GET /api/v1/private/settings?login=<hash>` | Bearer session | `{settings, activeSessions, discordId: null, rev}`, `activeSessions` counted in D1, `rev` the settings revision (0 for a record not pushed since revisions exist). Add `&fields=meta` for `{activeSessions, discordId: null, rev}` without the settings (the record is still read, for `rev`). |
| `POST /api/v1/private/settings?login=<hash>` | Bearer session | Merges `{settings}` into the record and stores the settings alone (a record's legacy `sessionTokens` go with its first real write), with a new `settingsRev`. Optional numeric `baseRev` next to `settings` (see Settings revisions): stored revision newer than `baseRev` → `409 {"error":"conflict","message","rev":<stored>}`, nothing written; success → `{"ok":true,"rev":<new>}`. Without `baseRev` (builds up to 1.17.1, pushes of a few keys) the success body stays the text `Saved`. A push that changes nothing is a `200` (with the stored `rev`) unless it is behind: the conflict is checked first. Too large: `413` with a JSON body naming the key (see Limits); daily budget spent: `503 daily_write_budget`; KV refusing the key twice: `503 kv_busy` (see Limits). |
| `DELETE /api/v1/private/settings?login=<hash>[&all=true]` | Bearer session | Removes the calling session (one D1 delete, the record is not touched); `all=true` is "Wipe all data" (see below). |
| `GET /api/v1/private/sessions?login=<hash>`, `DELETE /api/v1/private/sessions?login=<hash>&others=true` | Bearer session | `GET`: the login's live sessions, newest first, `{"sessions":[{"id":"<first 8 hex of the token's SHA-256>","createdAt":<ms>,"current":true\|false}]}`. `DELETE ...&others=true` ("Sign out other browsers"): revokes every session of the login but the caller's, `{"revoked":<n>}`; without `others=true`: `400 {"error":"bad_request"}`. D1 only, not rate limited (like the sign-out). |
| `GET /api/v1/public/visuals?login=<hash>` | none | Public visuals of one profile, `Cache-Control: public, max-age=300`. Read from the login's `public_visuals` row in D1, else from its KV record (see Data kept in D1); the answer is the same either way, byte for byte. |
| `GET /api/v1/public/visuals?logins=<h1>,<h2>,...` | none | Same, for up to 50 hashes in one call: `{"visuals": {<hash>: {...}}}`: one D1 query, then one bulk KV read for the hashes without a row only. Unknown hashes get the defaults, like the single form. 120 calls a minute per IP (see Limits). |
| `POST /api/v1/private/images?slot=avatar\|banner\|background` (raw image body, 2 MB, PNG/JPEG/GIF/WebP by magic bytes), `DELETE /api/v1/private/images?slot=`, `GET /img/<hash>/<slot>?v=` | Bearer session / none | Profile images uploaded from the editor, one KV value per slot (a new upload replaces the old), stored without their metadata (see Limits); `POST` answers `{"url": ".../img/<hash>/<slot>?v=<n>"}`. `GET` with the `v` of the stored upload serves it with `Cache-Control: public, max-age=31536000, immutable`; any other `v`, or none, answers `302` to the current `?v=` with `Cache-Control: no-store` and CORS headers, so a superseded URL saved in a profile or a history shows the current image instead of breaking, and no URL is ever cached with bytes it does not name. `404` only when the slot is empty. `DELETE` removes that slot: `204` (also when it was empty), write rate limit. Wipe deletes all three. |
| `GET /api/v1/private/calendar/token`, `POST /api/v1/private/calendar/token`, `DELETE /api/v1/private/calendar/token`, `POST /api/v1/private/calendar/update`, `GET /calendar/<token>.ics` | Bearer session / opaque token | Calendar links. `GET .../token` answers the live link, `{"token":"<token>"\|null}` (`Cache-Control: no-store`, no write, not rate limited), so another browser shows it rather than offering "Generate", which would revoke it. `POST .../token` registers a new link (`409 conflict` for a token already bound); `DELETE` is "Stop sharing": revokes the link and deletes the stored calendar (`204`, write rate limit). `.../update` then answers `410 {"error":"calendar_stopped"}` while the login has links and none is live, until a new one is registered (a login with no link row at all is not affected). |
| `POST /api/v1/private/subjects/report`, `GET /api/v1/private/subjects/state?slugs=` | Bearer session | Subject tracker. `report` takes one `{slug, url}` (write rate limit), reads the PDF's dates on a new slug or link and answers `first`, `known` or `changed`; two first reports of one slug at once both answer (the second gets `known`, one row). A new slug whose PDF download times out is not seeded (`{"status":"unknown","reason":"pdf_unavailable"}`) and the next reporter tries again; a PDF that cannot be read at all (error status, redirect off the subject hosts, over 16 MB) is still seeded with null dates, so its changes are seen. `state` reads up to 5 distinct slugs in one query (every build sends one). `name` is always `null` (the `projects` table is no longer read). |
| `GET /api/v1/private/export?login=<hash>` | Bearer session | "Download my cloud data": everything kept about the caller, `{"exportedAt","loginHash","settings","rev","sessions":[{"id","createdAt"}],"firstSignIn":<ms>\|null,"calendar":{"live","feedStored"},"images":["avatar",...],"publicVisuals":{...}}`, with `Cache-Control: no-store` and `Content-Disposition: attachment`. Never a token: sessions by their short id, settings keys ending in `TOKEN` (the calendar link, a session token an old build synced) as `"[redacted]"`. Writes nothing; write rate limit (the record, three image metadata reads, a few D1 queries). |
| `GET /api/v1/cluster/svg?url=` | none | Cluster maps (SVGs from `https://*.intra.42.fr` only); `502` when the host answers something unusable, or nothing in time (the extension falls back to its cached map). `/api/v1/cluster/svgs`, which read a KV key nothing ever wrote and no build called, is gone (404). |
| `GET /api/v1/public/announcement`, `POST` with `{secret, message, level?, links?}` (16 KB at most) | operator secret in the JSON body | Banner shown in the extension. An empty `message` clears it; the secret never goes in a query string (`DELETE` is gone). Unset `ANNOUNCEMENT_SECRET` closes the route (`403` before the body is read). `POST` is limited to 5 a minute per IP (its own bucket, see Limits), before the body is read, and the secret is compared in constant time; set it to 32 random bytes (`openssl rand -base64 32`, then `npx wrangler secret put ANNOUNCEMENT_SECRET`). `GET` is served from isolate memory for 5 minutes, the empty answer included (one KV read per isolate instead of one per profile page load); the isolate that took the `POST` serves the new banner at once, the others within 5 minutes plus KV's 60 s. |
| `GET /api/v1/public/stats` | none | Community counter (see "Data kept in D1"): totals and new users; `countries` is always `[]` (kept for extension builds up to 1.13.x, which read it). |
| `GET /gh/*` | none | GitHub raw proxy for campus data: raw.githubusercontent.com, then jsDelivr when the first answers an error status, throws or does not answer within 4 s (body included). The last upstream status is kept (a `404` is what makes the extension cache a campus without data), `502` when no source answered at all. |

Anything else answers 404 before touching KV or D1. Every error is JSON, `{"error":"<code>","message":"<English>"}` (plus `key`/`max` on a settings `413`, `rev` on a `409`), with CORS headers and the status each case always had, so builds that read the status see no change and the ones that show the text get it from `message`. The codes are stable, and the extension picks its translated message from them: `unauthorized` (401, and the 403s), `rate_limited` (429), `daily_write_budget` (503), `too_large` (413), `conflict` (409), `calendar_stopped` (410), `bad_request` (400, 405), `not_found` (404), `kv_busy` (503), `unsupported_image_type` (415, both the wrong type and a file that does not parse), `image_too_large` (413 on an image), `server_error` (500, 502, the key server's 503). A refused `Origin` gets its JSON `403` without CORS headers. Every private route answers one and the same `401` for a missing header, a wrong, revoked or expired token and an unknown login (the login parameter is sha256 of a public login, so a distinct "not found" would tell anyone who uses the extension); a request without a Bearer token is refused before any KV or D1 read, so anonymous scans cost nothing. The `login` parameter must be a login hash (64 lowercase hex characters).

## Sessions

- **In D1** (`sessions`, `src/sessions.ts`), not in the KV record any more: one row per signed-in browser, keyed by the login hash and the **SHA-256 of the token** (the token itself is never stored, so a dump of the table or of a record opens nothing). They used to be a `sessionTokens` array next to the settings, and every sign-in, sign-out and push rewrote both from one read that KV may serve up to 60 s stale: a push could drop a session opened a moment before, a sign-out racing a push brought the token back. D1 has no read replica here, so a sign-in, sign-out or revocation is seen at once, and none of them spends a KV write.
- **At most 10 per login** (a sign-in drops the oldest) and **refused once older than 365 days**, with the same `401` as a revoked one (every extension build answers a 401 with "Sign in again").
- **Records from before** keep their tokens in KV until the login's first request to this worker: that request copies them into D1, hashed (the newest 10, dated `LEGACY_SESSION_CREATED_AT` = 2026-09-25, so they expire on 2027-09-25 at the latest), and writes a `session_migrations` row in the same transaction. From then on the KV list is never read again; it goes with the record's next real push. No bulk migration (it would spend one KV write per user). A login with neither a record nor a marker is refused without any write.
- **Rolling back** to a worker from before D1 sessions signs out everyone whose record lost its `sessionTokens` (any push since) and every session opened since: the extension then offers "Sign in again". Deploying this worker again after such a rollback signs out, once more, the browsers that signed in during it on a login already copied to D1: its `session_migrations` row stops a second copy, so the tokens the old worker added to the record are never read. The rollback also brings back the sessions revoked in D1 since (a sign-out, *Sign out my other browsers*, the 365-day limit) for as long as their record still lists them in clear (no push since): the old worker checks that list, not D1.
- **Settings revisions**: the record carries `settingsRev`, `max(Date.now(), previous + 1)` at each settings write, so it only grows. A push that sends `baseRev` (the revision the browser last pulled or pushed) is refused with `409 conflict` when the stored revision is newer: a browser that never pulled used to overwrite every key another one had pushed, the friends list and the public avatar included. A stored revision older than `baseRev` is the browser's own write read back stale (KV may serve a copy up to 60 s old) and the push goes on. The conflict is checked before the "nothing changes" shortcut: a push of a few keys that happen to match would otherwise be answered the other browser's revision, which its sender cannot tell from its own write, and its next full push would overwrite that browser's keys. So a success never answers a revision newer than `baseRev` without having written it. The check is best effort for the same reason: two browsers pushing within a minute through different locations can both pass it. A push without `baseRev` is merged as before, and bumps the revision too. Records from before have none (`rev: 0`) until their next write.
- **Intra client pin**: `/auth/intra` only accepts a token whose `azp` (the client it was issued to) is in the comma-separated `JWT_ALLOWED_AZP` (`wrangler.json` `vars`: `"frontend-react"`, the Intra v3 front-end, read from its public bundle). Every client of the students-42 realm gets tokens signed with the same key and carrying the same login; the extension only ever sends profile-v3's. A refusal is the same `401` as an invalid token, and is logged as `[intra-auth] token refused: client "<azp>" is not in JWT_ALLOWED_AZP` (the client id only). An empty or missing variable turns the check off, so a 42 rename is undone by editing the variable.

## Limits

- **Rate limits** (`src/rate-limit.ts`): 10 writes a minute per login hash (sign-in once the token is verified, settings push, wipe, calendar link, stop and upload, image upload and delete, subject reports, the data export; signing out, of this browser or the others, is not limited), 30 well-formed `/auth/intra` attempts a minute per IP before any key work, 120 batch visuals calls a minute per IP before the bulk read (each call reads up to 50 keys, missing ones billed too: without it about 2,000 anonymous calls spend the 100,000 daily KV reads; a student sends one batch per friends list every 10 minutes, so a campus NAT stays far below), and 5 announcement `POST`s a minute per IP before the body is read (`admin`, its own bucket, so a guessing loop behind a campus NAT does not lock the campus out of signing in). "Per IP" is per address for IPv4 and per /64 prefix for IPv6 (one host holds a whole /64 and can use a new address for every request). The single-login visuals route and `/img/` are not limited: one read per call is the same ratio as the 100,000 daily Worker requests. Over a limit: `429` with `Retry-After: 60`. A push that changes nothing is neither written nor counted. The Workers rate limit bindings in `wrangler.json` (`WRITE_RL`, `ANON_RL`, `VISUALS_RL`, `ADMIN_RL`, free on every plan) are used when bound, and then they alone decide: `tests/config.test.ts` fails when their limits differ from `LIMITS` in `src/rate-limit.ts`; otherwise (local dev, tests, a fork without them) an in-isolate fixed window stands in. Both are best effort per colo/isolate: they make abuse slow and attributable, they do not make the shared 1,000 KV writes a day unexhaustible.
- **Daily KV write budget** (`src/budget.ts`, D1 table `kv_write_budget`): the namespace shares 1,000 writes a day and the rate limits alone allow 14,400 per login. Each settings push that writes, each image upload and each first sign-in's record first spends one unit of the login's day (200 at most) and of the namespace's (900, sign-ins up to 980; the rest covers the JWKS cache and the announcement, not counted). Past a cap: `503 {"error":"daily_write_budget"}` with `Retry-After` until 00:00 UTC, and nothing written (every build files that as a refusal, retried at most three times by the hub; a `429` would be retried every 65 s all day). A refusal writes no D1 row; deletes, sign-outs and wipes are never counted nor refused. If D1 fails the write is allowed and logged. Refusals are logged with the first 12 characters of the login hash and both counts, and `SELECT * FROM kv_write_budget ORDER BY n DESC` names who spent the day (rows are kept two days; a wipe does not reset them, or wiping would reset the cap).
- **KV busy**: KV takes one write per key per second, and the extension can send a second push as soon as the first answers. A settings push, an image upload or a first sign-in's record refused for that is retried once, about 1.1 s later (wall time, no CPU billed), from a fresh read of the record (a push written in between is merged, never rolled back; a retry that finds the same content stored writes nothing). Refused again: `503 {"error":"kv_busy"}` with `Retry-After: 2` (the sign-in leaves the record to the first push instead). KV's daily limit is not retried and stays a `500 server_error`.
- **Size caps**: settings push body and merged record 256 KB, any single string value 64 KB (a custom stylesheet, and the Customize presets that each copy it, went past the former 8 KB / 64 KB for real students), calendar upload 256 KB (`413`), calendar token body 4 KB, image 2 MB (`413`), and the two unauthenticated bodies, `/auth/intra` 32 KB and the announcement `POST` 16 KB (`413`, read before any other check). Bodies are dropped as soon as they go over, never buffered whole. A settings push over a cap answers `413` with `{"error":"too_large","key":<the string over 64 KB, the largest key of a record over 256 KB, or null for a body refused before parsing>,"max":<the cap>,"message":"Setting CUSTOM_CSS too large (max 64 KB)"}` (record: `"Settings too large (max 256 KB); largest: CUSTOM_PRESETS"`, body: `"Settings too large (max 256 KB)"`).
- **Image metadata** (`src/image-strip.ts`) is removed on upload, on the bytes (no re-encoding: pixels, animation and ICC colour profiles stay): JPEG keeps APP0, APP2 ICC and APP14 Adobe and drops every other APPn (Exif, XMP, IPTC, MPF...) and COM, plus anything after the first EOI (MPO frames, motion-photo videos, trailers); an Exif Orientation other than 1 is written back as a one-tag Exif block. PNG drops eXIf, tEXt, zTXt, iTXt, tIME, caBX and what follows IEND. WebP drops EXIF and XMP chunks and their VP8X flags and rewrites the RIFF size. GIF drops comment extensions and every application extension but NETSCAPE2.0/ANIMEXTS1.0 (loop) and ICCRGBG1012. A file that does not parse is refused (`415`), never stored raw.
- **Public visuals** are bounded again when served (URLs 2,048 characters, words and colours 64, numbers must be finite), so a record stored by an older worker is never re-served to every visitor as is. The `logtime` block carries display values only (colours, emoji, emoji value, rainbow palette): `LOGTIME_EMOJI_RATE` is not published (the extension long labelled it "Hourly Earning", so it can hold a real pay); visitors count with their own rate.
- **Outbound deadlines** (`FETCH_DEADLINES` in `src/utils.ts`), body included: 4 s per `/gh/` source, 5 s for Keycloak's key set (a stall is the sign-in's `503`, which the extension reads as "42's key server did not answer", not its own 20 s timeout), 8 s for a cluster map and for a subject PDF, redirects included (the extension waits 10 s). `tests/outbound-deadline.test.ts` fails on a `fetch()` without a signal.
- **CORS preflights** carry `Access-Control-Max-Age: 86400` (Chrome caps at 7,200 s), so an authenticated call is one invocation, not two.

## Data kept in D1

The schema is `migrations/` (`wrangler.json` `migrations_dir`), applied with `npx wrangler d1 migrations apply better-intra-d1 --remote`; `schema.sql` is the same schema in one file (a test checks they agree). Migrations only ever add (`CREATE ... IF NOT EXISTS`): `0001_baseline.sql` is the schema from before migrations and changes nothing on the live database.

- `sessions` (`login_hash`, `token_hash`, `created_at` in ms), `session_migrations` (`login_hash`, `migrated_at`): see Sessions.
- `users` (`hash`, `created_at`): one row per student who ever signed in, written on the first sign-in only; it feeds the totals of `/api/v1/public/stats` (hub About tab). The `country` column is no longer written or served. Rows from before still hold the two-letter country of their first sign-in until the operator clears them (see Operations notes); the column stays so no migration is needed.
- `calendar_ics`, `calendar_tokens`: calendar links, see below.
- `kv_write_budget` (`day` in days since the epoch, UTC, `login_hash` or `'*'` for the whole namespace, `n`): the daily KV write budget (see Limits), two days kept.
- `public_visuals` (`hash`, `settings`, `updated_at` in ms): the settings keys `/api/v1/public/visuals` reads (look, extras, avatar, banner, background, logtime display values), as JSON, per login. Written by a settings push when those keys change, and by one that finds the row saying something else than the record it writes (a copy of the record KV served stale, or a push cut short between its two writes; a comparison that fails is logged and does not fail the push); always before the KV record (a D1 failure writes nothing, a retry redoes both; a KV write that then fails for good, `kv_busy` or KV's daily limit, puts the row back to what the record holds); deleted by Wipe. The public routes read it first and fall back to the KV record for a login without a row (not pushed a public change since the table exists): no backfill, which would be a live operation for what the next push does anyway. A row is bounded to a few KB whatever the record holds (values no field would serve are left out).
- `subjects`: the subject tracker registry. `projects` (project names a 42 application used to fill) is no longer read: the answers keep `name: null`.
- A database created by the earlier schema also carries the 42-application tables (`eval_*`, `outstanding_*`, `*_stats_cache`, `logtime_history`, `cursus`, `correction_point_historics`, `profile_stats_cache`) and extra `users` columns; nothing reads them any more. Dropping them is the operator's call, by hand (after `npx wrangler d1 export better-intra-d1 --remote --output backup.sql`), never a migration: `migrations apply` would run it on every database.

## Data kept in KV

- `<login hash>`: the user record, `{settings, settingsRev}`, 256 KB at most. A record not pushed since sessions moved to D1 still carries its old `sessionTokens` (in clear); they are dead once the login's first request copied them, and go with the next push.
- `img:<login hash>:<slot>`: the uploaded image of that slot (metadata removed), with KV metadata `{type, v}`; `v` is the version its URL must carry.
- Small caches: `INTRA_JWKS_CACHE`, `ANNOUNCEMENT`. The legacy calendar links (`CALENDAR_TOKEN_*`) are no longer read: the live namespace held none on 2026-09-25. `CLUSTER_SVG_URLS` was read by the removed `/api/v1/cluster/svgs` and never written.

**Wipe all data** (`DELETE ...&all=true`) deletes, in this order: the calendar (revokes every link, deletes the stored ICS), the `users` row (the student leaves the community counter) and the `public_visuals` row, the uploaded images, the KV record (settings), then every session in D1. The day's `kv_write_budget` rows stay (two days at most). A failure in an earlier step leaves the session for a retry. Revoked calendar-link tombstones stay (token and login hash), so a wiped link can never be registered again; a login that never made a link is left with no `calendar_tokens` row (earlier workers wrote a revoked `wiped:<uuid>` marker there, which only served the retired KV links: the ones already written stay revoked and inert, and `DELETE FROM calendar_tokens WHERE token LIKE 'wiped:%'` removes them, with the owner's consent). So does the `session_migrations` row, so a location still serving the deleted record from its cache cannot copy its old tokens back.

## Operations notes

- **Migrations before deploying**: a deploy does not apply them. First `npx wrangler d1 migrations list better-intra-d1 --remote` (the live database starts with `0001_baseline.sql` to `0004_public_visuals.sql` pending; 0001 is a no-op there), then `npx wrangler d1 migrations apply better-intra-d1 --remote`, then deploy (`npm run deploy` refuses while one is pending). A worker deployed without `0002_sessions.sql` answers 500 on every private route and sign-in; without `0004_public_visuals.sql`, every push that changes the public look and every "Wipe all data" answer 500 (the public routes fall back to KV); without `0003_kv_write_budget.sql` the budget allows every write and logs a warning each time. A fork set up from an older `schema.sql` runs the same command before updating its worker.
- **Calendar links** live in the D1 table `calendar_tokens` (`migrations/0001_baseline.sql`); `src/handlers/calendar.ts` still creates it on first use until that migration is confirmed applied on the live database, and that code and its test go then. One live link per login: "Regenerate" revokes the previous link, "Stop sharing" (`DELETE .../calendar/token`) and "Wipe all data" revoke every link and delete the stored calendar, and a revoked link answers 404 and can never be registered again. After a stop, uploads answer 410 until a new link is registered, so a second browser that restored the synced `CALENDAR_SYNC_TOKEN` cannot put the timetable back. `GET .../calendar/token` tells any signed-in browser which link is live. Links made before this table (KV keys `CALENDAR_TOKEN_*`) are no longer read (none were left in the live namespace). Rolling back to a worker without the table would break the links made since.
- **Rolling back** past the settings revisions, the write budget and `public_visuals` (worker ce12afc or older): that worker ignores `baseRev` (a push from a new build gets the text `Saved` instead of `{ok, rev}`, which the extension takes as a success that brings no revision, so a stale browser's push is no longer refused until this worker is back), keeps `settingsRev` without bumping it, counts nothing, and serves visuals from KV. Its pushes do not update `public_visuals`, so after re-deploying this worker the rows of anyone who pushed meanwhile are stale: run `npx wrangler d1 execute better-intra-d1 --remote --command "DELETE FROM public_visuals"` (with the owner's consent) and the public routes fall back to KV until each login's next public push.
- `/api/v1/cluster/svg` only fetches SVGs from `https://*.intra.42.fr`; the subject tracker only fetches PDFs from `cdn.intra.42.fr` and `projects.intra.42.fr`.
- Unhandled errors come back as JSON 500 (`{"error":"server_error","message":...}`) with CORS headers, and are logged as `[worker] unhandled error: <METHOD> <path> <name>: <message>` (path only, never the query string). `observability.logs.invocation_logs` is off so that no request URL is persisted in Workers Logs (the `?login=<hash>` of each call, `/calendar/<token>.ics` links), and traces are off too. PRIVACY.md (Server logs) promises it: turning either on needs a PRIVACY.md change and a release note first (`tests/config.test.ts` pins both).
- **Preview URLs are off** (`"preview_urls": false`, with `"workers_dev": true` for the production URL): otherwise every past version keeps a `<version>-betterintra-remake.<account>.workers.dev` URL bound to the live KV and D1, running the code it had (before the rate limits, the body caps, the hourly-rate fix). It takes effect on the next deploy; afterwards an old version's preview host answers 404 and the production host 200.
- **One-off clean-ups**, by hand, each only with the owner's consent (they touch the live data): images uploaded before metadata removal existed go through `node scripts/strip-image-metadata.mjs --remote` (a dry run listing what would change), then `--apply` (one KV write per image that still carries metadata, metadata `{type, v}` kept so published URLs stay valid; a second run writes nothing). The countries stored before the change go with `npx wrangler d1 execute better-intra-d1 --remote --command "UPDATE users SET country = NULL"`. Neither runs at deploy.
- Tests: `npm test` (in-memory KV, SQLite-backed D1 built from `migrations/`, rate limit stub in `tests/helpers/fake-env.ts`). `tests/compat-1.17.1.test.ts` replays the requests of extension 1.17.1 and reads the answers the way it does: installed builds lag a release by weeks, so a route, a status or a success body they rely on only changes behind a new opt-in parameter or route. The extension's `tests/worker-contract.test.ts` runs the current client's flows (settings revision, sessions, calendar link, export, error codes) against `src/index.ts` and this fake environment when both repositories sit side by side, under jsdom: keep `tests/helpers/fake-env.ts` free of `new URL(..., import.meta.url)` file reads. Types: `npm run typecheck` (`tsc --noEmit -p .`, unused locals and parameters included).

## Deploy and roll back

Both are live operations: ask the owner first.

- **Deploy**: `npm run deploy` (`scripts/deploy.mjs`). It refuses a working tree with uncommitted changes, failing tests or type check, and a live database that has not applied every file of `migrations/` (it reads the live `d1_migrations` table, read-only, and prints the `npx wrangler d1 migrations apply better-intra-d1 --remote` to run first). Then it runs `wrangler deploy --tag <commit> --message "<commit> <subject>"`. `npm run deploy -- --dry-run` runs the same checks but the live one and builds without uploading. `npx wrangler deploy` alone still works but skips all of that (and `wrangler deploy --remote`, the old script, is refused by wrangler 4).
- **What is live**: `npx wrangler deployments list` (or `npx wrangler versions list`): each version's tag is its commit.
- **Check**: `curl https://betterintra-remake.maitox.workers.dev/api/v1/public/stats` answers `200` JSON.
- **Roll back**: `npx wrangler rollback <version-id> --message "<why>"` (without an id, wrangler offers the previous version). It restores the code and the config (bindings, variables, rate limits) only: never the D1 schema, the D1 rows or the KV data, which only move forward. Read "Rolling back" under Sessions and Operations notes before rolling back past a version that added a table: the sessions, calendar links and `public_visuals` rows written since stay, and an older worker ignores or misreads them.
